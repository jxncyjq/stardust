## 第一章 总览：AI 驱动的 RTL 开发闭环

### 1.1 当前痛点

芯片研发团队在使用 GitHub Copilot 生成 RTL 代码时面临三个核心挑战：

1. **生成质量不稳定** — LLM 对 Verilog/SystemVerilog 的理解不如 Python/JS 等高频语言，生成的 RTL 代码常出现语法错误、时序违规或不符合公司编码规范。参见 [[spec-coding-standards-rtl-013]] 中的高频违规清单。
2. **验证流程断裂** — 代码生成后需要手动切换到 EDA 工具做语法检查、编译、仿真，AI 辅助在"写完代码"后就断了。EDA 工具 CLI 用法参见 [[reference-eda-cli-tools-006]]。
3. **知识散落** — 设计文档、编码规范、历史 IP 库、EDA 工具用法分散在 Wiki/邮件/本地硬盘中，Copilot 无法有效利用。知识治理方案参见 [[design-obsidian-vault-structure-003]]。

### 1.2 目标架构

```
┌───────────────────────────────────────────────────────────┐
│                    AI-Driven RTL Pipeline                  │
│                                                           │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌────────┐ │
│  │ 知识管理  │──▶│ RTL 生成  │──▶│ 自动验证  │──▶│ 反馈闭环│ │
│  │ Obsidian │   │ Copilot  │   │ EDA CLI  │   │ 知识更新│ │
│  │ + Skills │   │ + Agent  │   │ + Skills │   │ + Agent│ │
│  └──────────┘   └──────────┘   └──────────┘   └────────┘ │
│       ▲                                           │       │
│       └───────────────────────────────────────────┘       │
│                    自我进化循环                             │
└───────────────────────────────────────────────────────────┘
```

四个阶段形成闭环：

|阶段|核心组件|详细文档|

## 第二章 RTL 开发文档生成

> **关联：** [[spec-coding-standards-rtl-013]] · [[reference-eda-cli-tools-006]]

### 2.1 设计文档是 AI 生成的"锚点"

Copilot 生成 RTL 代码的质量，80% 取决于喂给它的上下文质量。芯片设计文档应按以下结构标准化，以便被 Skill 引用和 Agent 调用：

```
docs/
├── architecture/
│   ├── top_level_spec.md            # → [[spec-top-level-arch-020]]
│   ├── module_hierarchy.md          # → [[spec-module-hierarchy-021]]
│   └── interface_protocol.md        # → [[spec-interface-protocol-022]]
├── coding_standards/
│   ├── naming_convention.md         # → [[spec-naming-convention-030]]
│   ├── clock_reset_policy.md        # → [[spec-clock-reset-policy-031]]
│   ├── fsm_guidelines.md            # → [[spec-fsm-guidelines-032]]
│   └── lint_rules.md                # → [[spec-lint-rules-033]]
├── ip_catalog/
│   ├── fifo_sync.md                 # → [[reference-ip-fifo-sync-040]]
│   ├── axi_master.md                # → [[reference-ip-axi-master-041]]
│   └── cdc_handshake.md             # → [[reference-ip-cdc-handshake-042]]
└── eda_reference/
    ├── vcs_usage.md                 # → [[reference-eda-vcs-050]]
    ├── xcelium_usage.md             # → [[reference-eda-xcelium-051]]
    └── iverilog_usage.md            # → [[reference-eda-iverilog-052]]
```

### 2.2 文档编写规范：让 AI 能读懂

每个设计文档必须包含符合 [[markdown.instructions]] 的 Front Matter。以 IP Catalog 条目为例：

```markdown
---
id: reference-ip-fifo-sync-040
title: 同步 FIFO 模块参考
aliases:
  - sync_fifo
  - 同步FIFO
type: reference
category: ip_catalog/basic
tags:
  - fifo
  - synchronous
  - buffer
  - rtl-ip
version: 1.2.0
created: 2025-06-15
updated: 2026-01-20
author: jxncyjq
status: published
parent: reference-ip-catalog-index-039
related_docs:
  - reference-ip-fifo-async-043
  - spec-clock-reset-policy-031
---

# sync_fifo — 同步 FIFO

## 功能描述
同步 FIFO，用于同一时钟域内的数据缓冲。

## 参数表
| 参数名       | 类型     | 默认值 | 说明            |
|-------------|---------|-------|----------------|
| DATA_WIDTH  | integer | 8     | 数据位宽        |
| DEPTH       | integer | 16    | FIFO 深度       |

## 端口定义
| 端口名  | 方向   | 位宽        | 说明       |
|--------|-------|------------|-----------|
| clk    | input | 1          | 系统时钟    |
| rst_n  | input | 1          | 低有效复位  |
| wr_en  | input | 1          | 写使能     |
| rd_en  | input | 1          | 读使能     |
| din    | input | DATA_WIDTH | 写数据     |
| dout   | output| DATA_WIDTH | 读数据     |
| full   | output| 1          | 满标志     |
| empty  | output| 1          | 空标志     |

## 时序约束
- 所有端口同步于 clk 上升沿
- rst_n 至少保持 2 个时钟周期
- 详见 [[spec-clock-reset-policy-031]]

## 编码要点
- 使用格雷码做读写指针
- full/empty 标志做组合逻辑输出
- FSM 编码风格遵循 [[spec-fsm-guidelines-032]]

## 相关模块
- 异步版本: [[reference-ip-fifo-async-043]]
- 上游消费者: [[reference-ip-axi-master-041]]
```

### 2.3 让 AI 自动生成参考手册

研发部门不需要手动写完所有文档。可以用 Copilot Agent 模式从现有代码库中自动提取并生成符合 [[markdown.instructions]] 规范的参考手册。

**Prompt 示例：**

```
@copilot Agent 模式

请扫描 src/rtl/ 目录下所有 .v 和 .sv 文件，对每个模块生成一份参考文档。

要求：
1. 输出格式严格遵循 [[markdown.instructions]] 规范
2. 每个文档必须包含完整的 Front Matter（id 使用 reference-ip-{模块名}-{序号}）
3. status 设为 draft，author 设为 jxncyjq
4. related_docs 字段自动填写被引用和引用它的模块 ID
5. 内容包含：功能描述、参数表、端口定义表、关键信号说明、状态机说明（若有）
6. 使用 <!-- @section: xxx --> 标记各章节

输出到 docs/06-Auto-Generated/ 目录，并生成 docs-index.json 更新片段。
```

**对应的 Agent 配置：**

```yaml
# .github/copilot-agents/doc-generator.yaml
# 关联文档: [[reference-copilot-agent-yaml-011]]
name: RTL Doc Generator
description: 从 RTL 源码自动生成符合文档规范的模块参考手册
trigger: manual
permissions:
  read: ["src/rtl/**", "docs/coding_standards/**"]
  write: ["docs/06-Auto-Generated/**", "docs/docs-index.json"]
workflow:
  - name: Scan RTL files
    run: |
      find src/rtl -name "*.v" -o -name "*.sv" | sort

  - name: Generate docs with front matter
    run: |
      copilot scan rtl-modules --format markdown --template docs/Templates/tpl-module-spec.md

  - name: Build cross-references
    run: |
      copilot suggest "Analyze module dependencies and populate related_docs fields"

  - name: Update docs-index.json
    run: |
      copilot generate "Append new entries to docs/docs-index.json"

  - name: Output
    run: |
      copilot report rtl-docs --output docs/06-Auto-Generated/
```

## 第三章 Skills 创建与应用

> **关联：** [[guide-copilot-skills-architecture-010]] · [[spec-rtl-gen-skill-001]] · [[spec-rtl-verify-skill-002]]

### 3.1 Skills 核心概念回顾

Skills 是 GitHub Copilot 的结构化知识管理机制，详见 [[guide-copilot-skills-architecture-010]]。

|组件|作用|RTL 场景举例|
|---|---|---|
|`SKILL.md`|决策树，指导 Agent 何时加载哪些资源|判断用户是要生成 RTL 还是验证 RTL|
|`references/`|技术文档和代码模板|编码规范、IP 模板、EDA 工具手册|
|`scripts/`|可执行脚本|lint.sh, compile.sh, run_sim.sh|

Skills 的核心优势是**渐进式加载**（约 500 tokens），相比 MCP（约 16,000 tokens）极大节省了上下文窗口。三级加载机制：

|级别|加载内容|Token 消耗|
|---|---|---|
|L1 元数据|Skill 名称、描述、触发条件|~50|
|L2 核心指令|SKILL.md 决策树|~300|
|L3 按需资源|references/ 中的具体文档|按需|

### 3.2 RTL 生成 Skill

> **详细规格：** [[spec-rtl-gen-skill-001]]

```
.github/skills/rtl-gen/
├── SKILL.md
├── references/
│   ├── naming_convention.md       # ← symlink → docs/02-Coding-Standards/
│   ├── fsm_template.sv
│   ├── axi_interface_template.sv
│   └── clock_domain_rules.md     # ← symlink → docs/02-Coding-Standards/
└── scripts/
    └── scaffold_module.sh
```

**SKILL.md：**

```markdown
# RTL Generation Skill

<!-- @section: trigger -->
## 触发条件
当用户请求生成 Verilog/SystemVerilog 模块时激活此 Skill。
关键词：生成模块、创建模块、新建 RTL、写一个 xxx 模块
<!-- @end-section -->

<!-- @section: decision-tree -->
## 决策树

### 用户要生成新模块？
→ 加载 references/naming_convention.md（来源: [[spec-naming-convention-030]]）
→ 根据模块类型选择模板：
  - 状态机模块 → references/fsm_template.sv
  - 总线接口模块 → references/axi_interface_template.sv
  - 通用逻辑模块 → 使用项目命名规范直接生成

### 用户要修改现有模块？
→ 加载 references/clock_domain_rules.md（来源: [[spec-clock-reset-policy-031]]）
→ 使用 Edit 模式做最小化修改
<!-- @end-section -->

<!-- @section: constraints -->
## 编码约束（强制执行）
以下规则来自 [[spec-coding-standards-rtl-013]]，任何生成的代码必须遵守：
- 所有 reg 在复位块中初始化
- 禁止使用 initial 块（仅限仿真）
- 时钟信号命名：clk_<domain>
- 复位信号命名：rst_<domain>_n（低有效）
- 参数使用全大写 + 下划线
<!-- @end-section -->

<!-- @section: output-format -->
## 输出格式
- 文件头包含版权声明和修改历史
- 每个端口必须有行内注释
- assign 和 always 块之间空一行
- 生成完成后自动调用 [[spec-rtl-verify-skill-002]] 做语法检查
<!-- @end-section -->
```

### 3.3 RTL 验证 Skill

> **详细规格：** [[spec-rtl-verify-skill-002]] **EDA 工具参考：** [[reference-eda-cli-tools-006]]

```
.github/skills/rtl-verify/
├── SKILL.md
├── references/
│   └── eda_tool_guide.md          # ← symlink → docs/04-EDA-Reference/
└── scripts/
    ├── lint.sh
    ├── compile.sh
    └── run_sim.sh
```

**scripts/lint.sh：**

```bash
#!/bin/bash
# RTL 语法检查脚本
# 参考: [[reference-eda-cli-tools-006]]
# 支持多种 EDA 工具，按优先级自动选择

FILE=$1
LOG_DIR=${2:-./logs}
mkdir -p $LOG_DIR

if command -v vcs &> /dev/null; then
    echo "[Lint] Using VCS..."
    vcs -lint=all -sverilog $FILE 2>&1 | tee $LOG_DIR/lint.log
elif command -v xvlog &> /dev/null; then
    echo "[Lint] Using Xcelium..."
    xvlog --sv $FILE 2>&1 | tee $LOG_DIR/lint.log
elif command -v iverilog &> /dev/null; then
    echo "[Lint] Using Icarus Verilog..."
    iverilog -t null -Wall $FILE 2>&1 | tee $LOG_DIR/lint.log
else
    echo "[Error] No supported EDA lint tool found."
    echo "请参考 [[reference-eda-cli-tools-006]] 安装所需工具"
    exit 1
fi

# 解析 lint 结果
if grep -qiE "error|fatal" $LOG_DIR/lint.log; then
    echo "[FAIL] Lint errors detected."
    exit 1
else
    echo "[PASS] Lint check passed."
    exit 0
fi
```

**scripts/compile.sh：**

```bash
#!/bin/bash
# RTL 编译脚本
# 参考: [[reference-eda-cli-tools-006]]

FILE=$1
TOP_MODULE=${2:-top}
LOG_DIR=${3:-./logs}
mkdir -p $LOG_DIR

if command -v vcs &> /dev/null; then
    echo "[Compile] Using VCS..."
    vcs -sverilog -full64 -top $TOP_MODULE $FILE \
        -o $LOG_DIR/simv 2>&1 | tee $LOG_DIR/compile.log
elif command -v xelab &> /dev/null; then
    echo "[Compile] Using Xcelium..."
    xvlog --sv $FILE && \
    xelab $TOP_MODULE -s sim_snapshot 2>&1 | tee $LOG_DIR/compile.log
elif command -v iverilog &> /dev/null; then
    echo "[Compile] Using Icarus Verilog..."
    iverilog -o $LOG_DIR/sim.vvp -s $TOP_MODULE $FILE \
        2>&1 | tee $LOG_DIR/compile.log
else
    echo "[Error] No supported compiler found."
    exit 1
fi

if [ $? -eq 0 ]; then
    echo "[PASS] Compilation successful."
else
    echo "[FAIL] Compilation failed."
    exit 1
fi
```

**scripts/run_sim.sh：**

```bash
#!/bin/bash
# RTL 仿真运行脚本
# 参考: [[reference-eda-cli-tools-006]]

TB_FILE=$1
DUT_FILE=$2
LOG_DIR=${3:-./logs}
mkdir -p $LOG_DIR

if command -v vcs &> /dev/null; then
    vcs -sverilog -full64 $DUT_FILE $TB_FILE -o $LOG_DIR/simv
    $LOG_DIR/simv 2>&1 | tee $LOG_DIR/sim.log
elif command -v iverilog &> /dev/null; then
    iverilog -o $LOG_DIR/sim.vvp $DUT_FILE $TB_FILE
    vvp $LOG_DIR/sim.vvp 2>&1 | tee $LOG_DIR/sim.log
fi

# 检查仿真结果
if grep -qi "PASS\|TEST PASSED\|All tests passed" $LOG_DIR/sim.log; then
    echo "[PASS] Simulation passed."
    exit 0
elif grep -qi "FAIL\|ERROR\|FATAL" $LOG_DIR/sim.log; then
    echo "[FAIL] Simulation failed."
    # 错误模式将被 [[design-knowledge-update-agent-004]] 收集
    exit 1
else
    echo "[WARN] Could not determine simulation result."
    exit 2
fi
```

### 3.4 完整闭环：RTL Pipeline Agent

> **关联：** [[reference-copilot-agent-yaml-011]]

将 [[spec-rtl-gen-skill-001]] 和 [[spec-rtl-verify-skill-002]] 串联成一个自动化 Agent：

```yaml
# .github/copilot-agents/rtl-pipeline.yaml
name: RTL Pipeline Agent
description: 生成 RTL 代码并自动完成语法检查、编译、仿真验证
trigger: manual
permissions:
  read: ["src/rtl/**", "tb/**", "docs/**", ".github/skills/**"]
  write: ["src/rtl/**", "tb/**", "logs/**"]
workflow:
  - name: Generate RTL
    run: |
      copilot generate "Based on design spec, generate RTL module"
      # 自动引用 rtl-gen Skill 中的模板和规范

  - name: Lint Check
    run: |
      bash .github/skills/rtl-verify/scripts/lint.sh src/rtl/new_module.sv

  - name: Compile
    run: |
      bash .github/skills/rtl-verify/scripts/compile.sh src/rtl/new_module.sv

  - name: Generate Testbench
    run: |
      copilot generate "Create testbench for new_module with edge cases"

  - name: Run Simulation
    run: |
      bash .github/skills/rtl-verify/scripts/run_sim.sh \
        tb/tb_new_module.sv src/rtl/new_module.sv

  - name: Report Results
    run: |
      copilot log summary --format markdown --output logs/pipeline_report.md

constraints:
  - 生成代码必须遵循 docs/coding_standards/ 中的所有规范
  - Lint 失败时自动尝试修复，最多重试 3 次
  - 不修改已有的生产代码
  - 验证失败日志交由 Knowledge Update Agent 分析
```

## 第四章 指令文档优化建议

> **关联：** [[reference-copilot-instructions-template-005]] · [[guide-copilot-skills-architecture-010]]

### 4.1 copilot-instructions.md 编写指南

项目根目录的 `.github/copilot-instructions.md` 是 Copilot 的"全局记忆"，每次会话自动注入上下文。

> **完整模板：** [[reference-copilot-instructions-template-005]]

```markdown
# Project Instructions for Copilot

## 项目概述
本项目为 XXX 芯片的 RTL 设计仓库，使用 SystemVerilog 2017 标准。

## 语言与工具链
- HDL: SystemVerilog (IEEE 1800-2017)
- 仿真器: VCS 2023.03 (主), Icarus Verilog (辅)
- Lint: Spyglass / VCS -lint
- 综合: Design Compiler 2023.03
- 详见: [[reference-eda-cli-tools-006]]

## 编码规范（强制）
以下规范详见 [[spec-coding-standards-rtl-013]]：
- 模块命名: 全小写 + 下划线, 如 `axi_master_ctrl`
- 信号命名: <类型前缀>_<功能描述>, 如 `r_data_valid`, `w_addr_ready`
- 时钟信号: `clk_<域名>`, 如 `clk_core`, `clk_bus`
- 复位信号: `rst_<域名>_n`, 低有效
- 参数: 全大写, 如 `DATA_WIDTH`, `ADDR_DEPTH`
- 禁止使用 `initial` 块（仅限 testbench）
- 所有 `always_ff` 块必须有复位分支
- 禁止在 `always_comb` 中使用锁存器推断

## 文档规范
- 所有文档遵循 [[markdown.instructions]] 规范
- 必须包含 Front Matter（id, title, type, status 等）
- 模块间引用使用 Obsidian 链接语法 [[doc-id]]

## 目录结构
- src/rtl/      — 设计源码
- tb/           — 测试平台
- docs/         — 设计文档（Obsidian Vault）
- scripts/      — 自动化脚本

## 可用 Skills
- [[spec-rtl-gen-skill-001|rtl-gen]]: RTL 代码生成
- [[spec-rtl-verify-skill-002|rtl-verify]]: RTL 验证

## 禁止事项
- 不要生成包含 `$display` 的设计代码（仅限 testbench）
- 不要使用 `logic [7:0] mem []`, 应使用参数化声明
- 不要在未声明时钟域的情况下使用 `@(posedge clk)`
```

### 4.3 让 AI 自动写参考手册并优化指令文档

利用 Copilot Agent 基于验证日志自动迭代指令文件，形成"写 → 查 → 学 → 改"的循环：

```
@copilot Agent 模式

任务一：自动生成参考手册
1. 扫描 src/rtl/ 所有 .v/.sv 文件
2. 按 [[markdown.instructions]] 规范生成模块参考文档
3. Front Matter 的 id 格式为 reference-ip-{模块名}-{序号}
4. 自动填充 related_docs 字段（基于 module 实例化关系）
5. 输出到 docs/06-Auto-Generated/，并追加 docs-index.json

任务二：自动优化指令文档
1. 分析 logs/ 目录下最近 20 次 lint/compile 的错误日志
2. 提取高频错误模式，归类为 syntax/timing/naming/CDC/reset
```

### 6.2 Knowledge Update Agent

> **详细规格：** [[design-knowledge-update-agent-004]]

```yaml
# .github/copilot-agents/knowledge-update.yaml
name: Knowledge Update Agent
description: 从验证日志和代码审查中提取教训，自动更新知识库
trigger: schedule  # 每周自动运行，或手动触发
permissions:
  read: ["logs/**", "src/rtl/**", "tb/**"]
  write: ["docs/05-Lessons-Learned/**",
          "docs/02-Coding-Standards/**",
          "docs/docs-index.json",
          ".github/copilot-instructions.md"]
workflow:
  - name: Collect error patterns
    run: |
      copilot scan logs/ --pattern "error|warning|fatal" --since "7 days"

  - name: Analyze and categorize
    run: |
      copilot suggest "Categorize errors into: syntax, timing, naming,
      CDC, reset. Identify root causes."

  - name: Generate lesson learned
    run: |
      # 使用模板 docs/Templates/tpl-lesson-learned.md
      # 输出文档遵循 [[markdown.instructions]] 规范
      copilot generate "Create lesson-learned entry with full Front Matter"

  - name: Update coding standards
    run: |
      copilot edit "Add new constraint rules to
      docs/02-Coding-Standards/ based on identified patterns.
      Update the 'updated' field in Front Matter."

  - name: Update instructions
    run: |
      copilot edit "Append new rules to
      .github/copilot-instructions.md #编码规范 section"

  - name: Update docs-index.json
    run: |
      copilot generate "Append new document entries to docs-index.json"

  - name: Create PR for review
    run: |
      git checkout -b docs/knowledge-update-$(date +%Y%m%d)
      git add docs/ .github/copilot-instructions.md
      git commit -m "docs: auto-update knowledge from verification logs"
      gh pr create --fill --reviewer @tech-lead
```

### 6.3 自我更新场景详解

**场景 A：从 Lint 错误中学习**

连续三个 PR 出现 `always_comb` 中锁存器推断的 lint 告警时，Agent 自动执行：

|步骤|动作|目标文档|
|---|---|---|
|1|新增踩坑记录|`05-Lessons-Learned/` → 新建 [[lesson-latch-infer-20260130]]|
|2|补充编码约束|[[spec-fsm-guidelines-032]] 新增一条规则|
|3|更新全局指令|[[reference-copilot-instructions-template-005]] "禁止事项"新增条目|
|4|新增 Review 规则|`.copilot/rules.md` 新增检测模式|
|5|更新文档索引|`docs-index.json` 追加新文档条目|

**场景 B：从新 IP 开发中沉淀知识**

当团队完成新 IP `axi_dma_ctrl` 的开发和验证后：

|步骤|动作|目标文档|
|---|---|---|
|1|自动生成模块参考|`06-Auto-Generated/` → 新建 [[reference-ip-axi-dma-ctrl-045]]|
|2|提示补充设计决策|用户在 Obsidian 中手动完善|
|3|注册到 IP Catalog|[[design-moc-ip-catalog-061]] 新增链接|
|4|更新 Skill 参考资料|[[spec-rtl-gen-skill-001]] references/ 新增条目|
|5|更新文档索引|`docs-index.json` 追加新文档条目|

**场景 C：基于覆盖率反馈优化 Testbench**

仿真完成后，Agent 分析覆盖率报告中的 uncovered bins，自动生成针对性的补充测试用例，并将覆盖率提升记录写入 [[lesson-coverage-gap-20260130]]。

### 6.4 CI/CD 集成

将知识更新融入 CI/CD，每次 PR merge 后自动触发：

```yaml
# .github/workflows/knowledge-feedback.yml
name: Knowledge Feedback Loop
on:
  pull_request:
    types: [closed]
    branches: [main]
    paths: ["src/rtl/**", "tb/**"]

jobs:
  update-knowledge:
    if: github.event.pull_request.merged == true
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Analyze verification logs
        run: |
          # 提取本次 PR 的 lint/compile 日志
          echo "Collecting verification artifacts..."

      - name: Trigger Knowledge Update Agent
        run: |
          # 调用 knowledge-update Agent
          echo "Triggering knowledge update..."

      - name: Create knowledge PR
        run: |
          # 如果有知识更新，自动创建文档更新 PR
          gh pr create --title "docs: auto-knowledge-update" --fill
```
